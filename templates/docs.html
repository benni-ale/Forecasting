Weighted Sentiment with Diffusion

Il Weighted Sentiment with Diffusion è una metrica che calcola il sentiment ponderato per rilevanza, considerando anche l'effetto di diffusione temporale delle notizie. Ogni notizia contribuisce al sentiment per più giorni, con un decadimento esponenziale nel tempo.

1. Struttura della Vista SQL

La vista ticker_daily_sentiment_view è costruita usando diverse Common Table Expressions (CTE) che processano i dati in fasi successive:

1.1. ticker_data

La prima CTE estrae i dati dei ticker dall'array JSONB ticker_sentiment presente in ogni articolo.

WITH ticker_data AS ( SELECT DATE(time_published) as date, jsonb_array_elements(ticker_sentiment) as ticker_info, time_published FROM articles WHERE time_published IS NOT NULL AND ticker_sentiment IS NOT NULL AND jsonb_array_length(ticker_sentiment) > 0 )

Perché questa struttura? Ogni articolo può contenere più ticker nel campo JSONB. jsonb_array_elements() "esplode" l'array creando una riga per ogni ticker, permettendo di processare ogni ticker individualmente.

1.2. ticker_scores

Estrae i valori numerici dal JSONB e li converte in tipi appropriati.

ticker_scores AS ( SELECT date, ticker_info->>'ticker' as ticker, (ticker_info->>'ticker_sentiment_score')::numeric as sentiment_score, (ticker_info->>'relevance_score')::numeric as relevance_score, ticker_info->>'ticker_sentiment_label' as sentiment_label, time_published FROM ticker_data WHERE ticker_info->>'ticker' IS NOT NULL AND ticker_info->>'ticker_sentiment_score' IS NOT NULL AND ticker_info->>'relevance_score' IS NOT NULL )
1.3. daily_aggregations

Aggrega i dati per ticker e giorno, calcolando le medie e i conteggi.

daily_aggregations AS ( SELECT ticker, date, AVG(sentiment_score) as avg_sentiment_score, AVG(relevance_score) as avg_relevance_score, AVG(sentiment_score * relevance_score) as weighted_sentiment, SUM(sentiment_score * relevance_score) as total_weighted_sentiment, COUNT(*) as article_count, ... FROM ticker_scores GROUP BY ticker, date )

Nota importante: weighted_sentiment è calcolato come AVG(sentiment_score * relevance_score), che rappresenta la media del prodotto sentiment × relevance per ogni articolo. Questo è diverso dal prodotto delle medie.

2. Generazione di Tutte le Date

Per calcolare correttamente il sentiment diffused, abbiamo bisogno di una riga per ogni giorno nel range, anche se non ci sono state notizie quel giorno. Questo permette al sentiment diffused di essere calcolato anche per i giorni senza nuove notizie.

2.1. all_dates
all_dates AS ( SELECT DISTINCT ticker, generate_series( GREATEST(MIN(date), CURRENT_DATE - INTERVAL '1 year'), CURRENT_DATE, INTERVAL '1 day' )::date as date FROM daily_aggregations GROUP BY ticker )

Perché generate_series? Crea una serie di date consecutive per ogni ticker, dal primo articolo (o massimo 1 anno fa) fino ad oggi. Questo garantisce che ogni giorno abbia una riga, anche senza notizie.

2.2. all_days_with_aggregations
all_days_with_aggregations AS ( SELECT ad.ticker, ad.date, da.avg_sentiment_score, da.avg_relevance_score, da.weighted_sentiment, ... FROM all_dates ad LEFT JOIN daily_aggregations da ON ad.ticker = da.ticker AND ad.date = da.date )

Perché LEFT JOIN? Il LEFT JOIN mantiene tutte le date da all_dates, anche quando non c'è corrispondenza in daily_aggregations. I giorni senza notizie avranno valori NULL per i campi aggregati, ma avranno comunque una riga nella vista.

3.3. Implementazione SQL
diffused_sentiment AS ( SELECT d1.ticker, d1.date, ... COALESCE( SUM(d2.weighted_sentiment * POWER(0.5, (d1.date - d2.date)::numeric / 7.0)) FILTER (WHERE d2.weighted_sentiment IS NOT NULL), 0 ) as weighted_sentiment_diffused FROM all_days_with_aggregations d1 LEFT JOIN all_days_with_aggregations d2 ON d1.ticker = d2.ticker AND d2.date <= d1.date AND d2.date >= d1.date - INTERVAL '30 days' GROUP BY ... )
3.4. Perché questo LEFT JOIN?

Il LEFT JOIN con condizioni di data nel ON è cruciale per le performance:

  • Condizione nel JOIN: d2.date <= d1.date AND d2.date >= d1.date - INTERVAL '30 days'
  • Questo limita il prodotto cartesiano fin dall'inizio, invece di generare tutte le combinazioni e poi filtrare
  • PostgreSQL può usare indici e ottimizzazioni per questo tipo di JOIN
  • Riduce drasticamente il numero di righe da processare

Nota: Se avessimo messo le condizioni nel WHERE invece che nel ON, PostgreSQL avrebbe generato un prodotto cartesiano completo prima di filtrare, causando performance disastrose.

3.5. Perché Somma e non Media Ponderata?

Usiamo la somma dei sentimenti con decay, non la media ponderata, perché:

  • La somma riflette l'intensità cumulativa del sentiment nel tempo
  • Con un solo articolo, la media ponderata darebbe sempre lo stesso valore (problema che avevamo prima)
  • La somma con decay mostra chiaramente come il sentiment diminuisce nel tempo anche con un solo articolo
  • È più intuitivo: più notizie = sentiment più alto, che decresce nel tempo

5. Esempio Pratico

Supponiamo di avere un articolo il 2025-12-19 con weighted_sentiment = 0.0054:

  • 2025-12-19: 0.0054 × 0.50/7 = 0.0054 × 1.0 = 0.0054
  • 2025-12-20: 0.0054 × 0.51/7 ≈ 0.0054 × 0.906 ≈ 0.0049
  • 2025-12-21: 0.0054 × 0.52/7 ≈ 0.0054 × 0.821 ≈ 0.0044
  • 2025-12-26: 0.0054 × 0.57/7 = 0.0054 × 0.5 = 0.0027 (metà dopo 7 giorni)
  • 2026-01-02: 0.0054 × 0.514/7 = 0.0054 × 0.25 = 0.00135 (un quarto dopo 14 giorni)

Se ci sono più articoli, i loro contributi vengono sommati. Ad esempio, se il 2025-12-20 c'è un nuovo articolo con weighted_sentiment = 0.003, il sentiment diffused per quel giorno sarà:

  • Contributo del 2025-12-19: 0.0054 × 0.51/7 ≈ 0.0049
  • Contributo del 2025-12-20: 0.003 × 0.50/7 = 0.003
  • Totale: 0.0049 + 0.003 = 0.0079

6. Query Utilizzate nell'Applicazione

6.1. Query per ottenere i dati aggregati
SELECT ticker, date, weighted_sentiment, weighted_sentiment_diffused, article_count FROM ticker_daily_sentiment_view WHERE ticker = 'AAPL' AND date >= CURRENT_DATE - INTERVAL '30 days' ORDER BY date ASC

Questa query viene eseguita quando l'utente seleziona un ticker nella pagina Analytics. La vista è già pre-calcolata, quindi la query è veloce anche con molti dati.

6.2. Query per il confronto con il prezzo

Per confrontare il sentiment con il prezzo delle azioni, l'applicazione:

  1. Recupera i prezzi storici dall'API Alpha Vantage
  2. Recupera i sentiment dalla vista SQL
  3. Applica forward fill ai prezzi (mantiene l'ultimo prezzo per i giorni di chiusura del mercato)
  4. Normalizza entrambe le serie usando Min-Max
  5. Allinea i dati per data

Perché forward fill per i prezzi ma non per il sentiment? I prezzi delle azioni hanno senso anche nei giorni di chiusura (ultimo prezzo noto), mentre il sentiment deve riflettere solo i giorni con effettive notizie. Un giorno senza notizie deve avere sentiment NULL o 0, non il valore del giorno precedente.

7. Considerazioni sulle Performance

  • Vista materializzata? No, è una vista normale. Potrebbe essere materializzata se le performance diventano un problema, ma richiederebbe refresh periodici.
  • Indici: Gli indici su time_published e il GIN index su ticker_sentiment aiutano le performance delle query base.
  • Ottimizzazione del JOIN: Le condizioni di data nel ON del JOIN sono cruciali per evitare prodotti cartesiani enormi.
  • Limite di 30 giorni: Il calcolo considera solo gli ultimi 30 giorni per bilanciare accuratezza e performance. Dopo 30 giorni, il contributo è trascurabile (< 0.530/7 ≈ 0.06).
